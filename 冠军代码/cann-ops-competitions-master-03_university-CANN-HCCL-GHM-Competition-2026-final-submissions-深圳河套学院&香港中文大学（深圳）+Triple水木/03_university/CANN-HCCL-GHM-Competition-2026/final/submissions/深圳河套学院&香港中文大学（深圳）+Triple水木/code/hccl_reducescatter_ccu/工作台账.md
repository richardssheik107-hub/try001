# ReduceScatter 决赛实验台账（压缩版）

用途：只为上下文恢复保存可操作结论。历史实现细节以Git为准，不再保留逐行过程记录。

## 测试点映射与固定约束

- 每种拓扑依次为小数据、512 MiB、400 MiB+4B；性能主要观察测试点11/12、14/15、17/18。
- 小数据固定采用队友 `Final-pro` 已验证的 `SmallBufferTile`：每个IO Die在CCU Buffer内完成所负责source的tile规约，双Die最后普通二路合并。
- 大数据每个IO Die最多两个CCU Mission：Mission 0通信，Mission 1本地规约。增加Host Thread不能增加Mission或物理带宽。
- 不运行本地 `hccl_vm`：本机完整编译依赖过重。只做源码检查和 `bash build.sh`。
- `Final-pro/`是用户提供的未跟踪参考目录，不修改、不提交。

## 已验证算法结论

### 小数据

- S1递归减半/Direct融合没有稳定收益，并轻微拖慢大Kernel。
- S2专用小Kernel有效：约2×8 29 us、4×1 21 us、8+4 30 us。
- 后续迁移队友CCU Buffer方案后，小数据由队友版本固定，不再与大数据实验混改。

### 2×8与8+4大数据

- 最优稳定基线为S9 MixedRoute + HBM Reduce。
- 数据分成A/B：Mesh生成/规约本Server贡献，Clos传递Server partial和B；两Die通信并行，Bank通信与上一Bank规约重叠。
- self完整复制到output；Mesh slot执行 `REDUCE_MESH_SLOTS_TO_DST`，Clos slot执行 `FOLD_SLOTS_IN_PLACE`，最后普通二路合并。
- 2×8可使用按Die角色裁剪；8+4对Kernel翻译形状敏感，早期过度拆Mode曾明显劣化。因此算法优化必须保持拓扑独立可回退。
- S9参考：2×8约1.20 ms / 930 us；8+4约1.68 ms / 1.30 ms。

### 4×1大数据

- 已验证最佳家族是三个远端slot、self直接复制到output、12:3:1三轮Fade-out。
- 512 MiB总输入时每Rank输出128 MiB，三轮约96/24/8 MiB。三轮分别使用常驻scratch，不复用Bank；通信下一轮时Local Mission规约上一轮。
- 当前最佳已升级为S12：每轮分4片，每片三路Read到齐后立即由零Channel Local Mission规约，通信Mission继续发射后续片。实测2.34 ms / 1.84 ms。
- 3:1两轮比12:3:1三轮慢约10 us；16:4:1与9:3:1没有胜过12:3:1。
- 直接ReadReduce、远端直读CCU Buffer以及大数据CCU Buffer Loop均未取得性能收益或触发Checker限制。
- 历史参考：S2约2.43 ms / 1.88 ms；S9约2.46 ms / 1.93 ms。

## CCU Buffer大数据实验的固化结论

- 单个 `CcuBuffer` 参与Read/Copy/Reduce时长度不得超过4 KiB；连续申请多个MS不能用首句柄执行8 KiB操作。
- 每Die默认128个4 KiB MS。资源在Kernel注册时确定，重复Launch不会重复申请。
- 8路细粒度LoopGroup会使Checker图过大；减少lane、增大每lane粒度可使功能Pass，但性能仍明显慢于S9。
- 已Pass的MixedRoute Buffer几何最终仍劣化：2×8从S9约1.20/0.930 ms退到约1.56/1.23 ms，8+4从1.68/1.30 ms退到1.97/1.56 ms。
- 原因不是“CCU Buffer硬件慢”，而是当前路径为远端→HBM slot→MS→Reduce→HBM，增加微块搬运、Event、LoopGroup与图展开，并破坏大块通信/规约重叠。
- 因此大数据回退S9 HBM Reduce；小数据继续使用CCU Buffer，因为小数据固定开销和容量条件不同。

## S10：4×1每Channel双outstanding交错Read

- 基点：小数据=`Final-pro SmallBufferTile`；2×8/8+4大数据=S9 HBM MixedRoute；4×1=S9 12:3:1三Bank Fade-out。
- Context tag：`hccl_custom_reducescatter_fade_split_read_4x1_v1`。
- 唯一大数据实验变量：每轮中每个远端peer的大Read等分为两个FP32对齐请求，发射顺序为：

```text
peer0-half0, peer1-half0, peer2-half0,
peer0-half1, peer1-half1, peer2-half1,
EventWait(all 6)
```

- 三条物理Channel不变，每Channel outstanding由1增加到2；12:3:1、三Bank、self-copy、Local Reduce和Notify关系不变。
- 功能：提交环境全部Pass。
- 性能：2×8约1.20/0.930 ms，4×1约2.48/1.91 ms，8+4约1.68/1.30 ms；作为当前稳定大数据基线。
- 对应专项说明见 `4x1优化台账.md`；后续通用实验仍回到本台账记录。

## S11：固定两组 Speculative Reduce（已回退）

- 每个MixedRoute Bank或4×1 Pass把输入root固定分为两组；group0到齐后先规约，通信Mission继续等group1，最后合并两组。
- 功能：18个测试点全部Pass；Git实验记录为`f9381dc`。
- 性能：六个大点累计约劣化1.6%。2×8为1.23/0.949 ms，4×1为2.48/1.98 ms，8+4为1.69/1.32 ms。
- 初赛分组依赖的是15路A2A中8路与6路的自然长尾差，且每组只增加一次连续大块Reduce；决赛4×1只有3条基本等长Read，固定1+2分组几乎没有可隐藏窗口，EventRecord/Wait成为额外开销。
- 结论：通过`73a1054`回退到S10粗粒度同步；后续若再做提前Reduce，必须利用可测量的自然长尾，不再按路数平均固定分组。

## S12：4×outstanding子片级规约与零Channel Mission

- 基点：小数据与2×8/8+4大数据不变；4×1仍保留12:3:1、三个远端HBM slot和self-copy。
- 每个Fade pass分成4个连续子片。通信Mission按子片交错发射`4 chunks × 3 peers = 12 Reads`；子片的3路Read全部完成后，通过命名Event立即释放对应Local Launch，无需等待整个pass。
- 新增专用`CcuReduceScatterFadeLocalKernel`：先折叠三个远端slot，再加到已初始化的output子片。该Kernel注册参数`channelCount=0`，Kernel本体也不引用Channel，不存在placement anchor或失败后回退S10的分支。
- hcomm源码结论：`HcommCcuKernelRegister`的`dieId`当前被忽略；零Channel Kernel的`SelectDie()`固定选第一个启用Die，即比赛环境中的Die0。通信Kernel则被Clos Channel钉在其物理Die。因此Clos=Die1时真正实现跨Die overlap；Clos=Die0时仍是同Die。当前尚未加硬检查验证所有rank的Clos都在Die1。
- Context tag：`hccl_custom_reducescatter_fade_4outstanding_cross_die_v1`。
- 功能：18个测试点全部Pass。
- 2026-07-30性能：总分221.87；2×8为1.20 ms / 929 us，4×1为2.34 ms / 1.84 ms，8+4为1.68 ms / 1.30 ms，小数据16/13/16 us。
- 相对S10的4×1 2.48/1.91 ms，512 MiB改善约5.6%，400 MiB+4B改善约3.7%；也超过S2的历史最佳4×1成绩。其他两种拓扑基本持平，说明收益集中在新的4×1流水。
- 判断：性能增益强烈支持“子片到齐即规约 + 通信/规约资源重叠”有效，当前版本应作为新的功能与性能基线保留。

## S13：可配置4×1分段

- 将S12的`12:3:1 × 每轮4切片`扁平化为可配置权重，首测`3:3:3:3:3:1`；128 MiB输出对应24/24/24/24/24/8 MiB。仅需修改`SEGMENT_4X1_WEIGHTS`，支持1～16段任意正权重，尾段吸收对齐余数。
- 通信一次Launch发射6段×3 peer Read，每Channel最多4 outstanding，按4+2两批；每段三路到齐后独立Record命名Event。
- Local收缩为一次Launch：先self-copy，再逐段Wait并执行`(slot0+slot1) + (output+slot2)`两层树。相对S12，Local Launch从13降到1，LocalReduce从36降到18，Reduce EventWait从36降到12。
- Comm ABI从9参降到6参；Reduce只Launch一次8参。删除最终`reduce→comm` Notify/Wait，远端Read全部完成后即开始最终跨rank barrier，与本地规约重叠。
- 首次提交暴露地址语义错误：各Rank错误发布了`input + recvBytes * sourceRank`，导致rank 0从rank 1读取偏移128 MiB而非0。现改为发布完整`input`基址，由目标Rank在Fetch时统一增加`recvBytes * myRank`。
- Kernel及辅助命名统一为`Comm/Reduce + General/4X1/Small`，旧`SingleLayer/LocalKernel/Generic`命名已清除。
- Context tag：`hccl_custom_reducescatter_4x1_segmented_333331_v1`。修正后18点功能Pass。
- 2026-07-30性能：总分221.19；2×8为1.21 ms / 931 us，4×1为2.38 ms / 1.86 ms，8+4为1.68 ms / 1.30 ms，小数据16/13/16 us。相比S12，4×1回退约40/20 us，其他拓扑基本持平。
- 最可疑变量是尾部outstanding下降：S12是`4×24 MiB → 4×6 MiB → 4×2 MiB`，而S13是`4×24 MiB → 24 MiB + 8 MiB`，最后32 MiB只有2个独立段。仅减少Launch/操作数未自动转化为性能收益。

## S14：恢复S12粒度，单独测试树形规约与调度精简

- 4×1分段权重改为`12,12,12,12,3,3,3,3,1,1,1,1`，权重和64。128 MiB输出精确恢复S12的`4×24 MiB → 4×6 MiB → 4×2 MiB`通信粒度与每Channel 4 outstanding。
- Context tag更新为`hccl_custom_reducescatter_4x1_segmented_s12grain_tree_v1`，避免与S13的不同Kernel翻译结果混用。
- 保留S13的单次Comm Launch、单次Reduce Launch与完整self-copy；本轮不拆LocalCopy，避免同时改变初始化粒度。
- 4×1的两层树Reduce保留，各段末级Reduce连续发射后再按Event汇总Wait；用于隔离测量减少Launch、树形规约和减少串行Wait的净效果。
- 同时包含不改变算法的结构精简：Small ABI 9参缩为8参，删除无用容器/旧Mode/不可达分支，统一Token获取和MixedScratchLayout派生数据。
- General Reduce实验性保留Mesh/Fold树形规约、8+4两个不重叠Clos partial并行ReadReduce，以及Mesh/Clos分别提前进入最终Barrier。因此S14的2×8/8+4结果也是这些改动的功能与性能验证。
- 性能待提交环境返回；若4×1恢复或超过S12，说明S13主要损失来自分段几何；若仍明显落后，则优先回查单Launch消费顺序或延后Wait。
- 首次提交中2×8与8+4的四个大数据点全部RE：Checker报CCL scratch越界和并行读写冲突。根因是General树Reduce会把部分scratch源slot作为中间写目标，不再符合MixedRoute尾Bank只为实际尾块保留空间的布局；同时Clos partial并行与Barrier提前破坏了Checker可证明的完整output先后关系。
- 修正版将2×8/8+4的Mesh/Fold恢复固定目标的线性Reduce+Wait，Clos partial恢复逐source `ReadReduce+Wait`，两个Comm Mission恢复等完整output后再进入Barrier。4×1的12段粒度、单Launch、两层树Reduce和延后末级Wait保持不变，因此修正后的S14只对4×1做性能实验。
- 后续将Mesh/Fold树改为不保存`LocalAddr`容器的原地分层树：每层从slot基址重建左右游标，层内并行规约不重叠slot，层间Wait，最后才将slot0加入output。这避免CCU DSL地址对象在C++容器中潜在共享底层表达式而产生超前地址。Clos partial与最终Barrier仍保持已Pass的串行顺序，新tag为`hccl_custom_reducescatter_mixed_hbm_safe_tree_v3`。
- 安全树修正版已在提交环境18个测试点全部Pass，证明上一版RE来自地址表达方式而非Checker禁止树形结构。2026-07-30性能：总分221.26；2×8为1.25 ms / 948 us，4×1为2.36 ms / 1.89 ms，8+4为1.71 ms / 1.31 ms，小数据16/13/16 us。相对S12六个大数据点均未改善，其中2×8退化最明显，因此MixedRoute安全树和4×1延后末级Wait均判定为负优化。

## S15：跨资源重叠实验

- 4×1通信由三个硬批次改为4-lane有序滚动窗口：先发射0～3，然后按segment顺序等待lane，每消费一个lane就在等待下一lane前补发`segment+4`。CCU没有wait-any，因此不宣称按实际任意完成顺序补发；outstanding上限、段粒度和每Channel顺序不变。
- 4×1完整self-copy拆为12个不重叠段，由新增channel-free Copy Mission一次异步发射；每段copy完成后用独立命名LocalNotify释放Reduce Mission。Reduce同时等待远端段和self段，不再有128 MiB完整copy栅栏。
- 源码确认每Die只有2个Mission资源，且无Channel Kernel固定选第一个启用Die。激进版使用三个Kernel：通信Mission留在Clos Die，Copy+Reduce两个无Channel Mission用满第一个启用Die的两个槽，以实现copy/reduce跨Mission重叠。若某Rank的Comm也落在该Die，注册将直接失败；本实验不含fallback，用评测暴露实际placement边界。
- 8+4的两个不重叠Clos A partial使用不同Event bit同时`ReadReduce`，再一次Wait。最终Barrier仍等完整output，不再混入S14首版的提前Barrier变量。
- 根据S14结果，撤回MixedRoute的Mesh/Fold树形规约，恢复固定output/slot0目标的线性`LocalReduce+Wait`；4×1每段末级Reduce也恢复立即Wait。S15只保留能够增加通信、Copy、Reduce跨资源重叠的变量，避免再次混入已确认的负优化。
- 首次提交发现4×1实际只有一个启用IO die，每die最多两个Mission，Comm+Reduce+独立Copy的第三个Mission注册返回`ret=7`。修正版将分段self-copy合入Comm Mission：每个lane同时发射三路远端Read和一路LocalCopy，四个Event bit全部完成后分别发布远端/self readiness，Reduce Mission仍按段立即消费。保留四lane滚动窗口、分段Copy与通信重叠、分段完成即Reduce，只将不可注册的三Mission布局收缩为Comm+Reduce两个Mission。
- Context tag：4×1=`hccl_custom_reducescatter_4x1_sliding_fused_copy_v3`，MixedRoute=`hccl_custom_reducescatter_mixed_linear_parallel_clos_v5`。
- 2026-07-31性能：总分221.69；2×8为1.20 ms / 932 us，4×1为2.37 ms / 1.82 ms，8+4为1.70 ms / 1.31 ms，小数据16/13/16 us。相对S12，4×1的400M点改善20 us，但512M退化30 us；8+4双Clos partial并行退化约20/10 us，判定为负优化。

## S16：平滑分段与Reduce Mission隐藏self-copy

- 2×8与8+4均恢复S12/S9最优线性路径；撤回两个Clos partial并行`ReadReduce`，恢复逐source `ReadReduce+Wait`。
- 4×1权重从`12,12,12,12,3,3,3,3,1,1,1,1`改为和仍为64的`12,12,12,8,8,4,4,2,1,1`。512M总输入时每Rank输出128 MiB，对应24/24/24/16/16/8/8/4/2/2 MiB，减小24→6 MiB的突变。
- 分段self-copy从Comm Mission移入Reduce Mission。每段先异步`LocalCopy(self→output)`，再等待该段三路远端Read；远端到齐后等待copy Event确认写依赖，然后执行两层树Reduce。目标是用远端等待隐藏本地copy，同时避免copy占用Comm Mission。
- 仍只注册Comm+Reduce两个Mission，无fallback；4-lane有序滚动窗口保持不变。Context tag：4×1=`hccl_custom_reducescatter_4x1_smooth_reduce_copy_v4`，MixedRoute=`hccl_custom_reducescatter_mixed_linear_serial_clos_v6`。
- 提交前进一步收敛小尾段：权重调整为总和仍为64的`12,12,12,9,8,5,3,2,1`，相邻下降倍率不超过2。512M总输入时对应24/24/24/18/16/10/6/4/2 MiB，只有最后一个远端Read为2 MiB；Context tag更新为`hccl_custom_reducescatter_4x1_smooth_single_tail_v5`。

## S17：4×1两轮Recursive Halving（首版已实现，待评测）

### 算法与数据量

- Rank按0～3编号。第一轮配对`0↔2, 1↔3`，每Rank交换并规约两个最终输出块，共`2S`；第二轮配对`0↔1, 2↔3`，每Rank交换第一轮生成的一个partial，共`S`，其中`S=recvBytes`。每Rank总跨机接收量仍为`3S`，与当前三对端All-to-All相同。
- 第一轮后，`0/1`分别持有最终块0/1所需的两组partial，`2/3`分别持有最终块2/3所需的两组partial；第二轮仅做一次二路合并得到最终输出。
- 512M总输入时`S=128 MiB`：第一轮256 MiB、第二轮128 MiB；400M点约为200 MiB+100 MiB。首版曾使用`4S` scratch，但评测实际CCL只有400 MiB，512M点因申请512 MiB直接失败。修正版将第一轮两个远端块原址规约为outgoing/retained partial，scratch降为`2S`，512M点仅需256 MiB。

### 严格通信时序

- 两轮通信共享每Rank固定的Clos总带宽`4V`，因此第二轮绝不能提前与第一轮重叠。Comm Mission必须先发射并等待第一轮全部Read完成，再按固定顺序发射第二轮Read。
- 第一轮和第二轮内部均保持相同的分段顺序及每Channel有序提交。异步请求的物理完成次序不作为正确性假设；第一轮结束使用本地EventWait覆盖全部第一轮网络请求，保证两轮网络不重叠。
- 第一轮优先传输并规约“第二轮将被对端读取”的outgoing partial，再处理本Rank最终保留的另一半。这样outgoing partial在第一轮后半段通信期间已经获得至少约`S/4V`的自然规约距离；第二轮又按相同片序消费，因此越靠后的partial拥有越长的第二轮消费距离。
- 不采用“第一片partial完成即启动第二轮”的跨轮流水，因为这会让两轮竞争同一`4V`并缩短天然距离；也不在第一轮结束后等待全部规约完成，否则会暴露本可隐藏的内存规约尾部。

### Mission划分

- 保持两个Mission，无fallback。
- `Comm Mission`：一次地址约定/交换；第一轮与`rank xor 2`的大块分段Read和全轮EventWait；随后第二轮与`rank xor 1`（低半组）或对应相邻Rank的大块分段Read；最后生命周期Barrier。它只负责网络，不执行LocalCopy/LocalReduce。
- `Reduce Mission`：第一轮每片到达后执行self初始化与二路规约，写入固定partial区；第二轮每片到达后把远端partial与本地partial二路规约到output。它与Comm Mission并行，使第一轮规约隐藏在第一轮剩余通信及第二轮同序消费距离中。
- 不使用单Mission：若同一队列逐片`Wait→Reduce`，会阻塞后续网络发射；若先等待完整第一轮再Reduce，则失去第一轮通信/规约重叠。两个Mission是保留算法流水的必要条件，而不是单纯增加Host线程。

### 首版同步策略与风险

- 首版没有跨Rank partial-ready Notify，400M点被Checker准确报告`partialSend`写与partner第二轮Read并行，证明天然时差只能隐藏性能开销，不能作为可证明的正确性依赖。
- 修正版在outgoing四片全部原址规约完成后只记录一次本地组级Event。Comm在第一轮八个网络Read全部结束后等待该Event，再与`rank xor 1`通过Channel bit4完成一次双向Notify握手，然后启动第二轮。retained四片不加入该栅栏，仍与第二轮通信重叠。
- 不增加逐片跨Rank通知，也不等待第一轮全部规约；因此理想状态仍只暴露第二轮最后一小片最终二合一规约与一次固定握手开销。
- 性能风险是单对端Channel能否接近跑满`4V`。第一轮采用较大分段和多outstanding；第二轮才使用平滑fade-out，避免第一轮小尾片降低带宽。
